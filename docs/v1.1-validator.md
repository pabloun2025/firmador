# Validador v1.1 — preparado, no desplegado

Esta entrega implementa únicamente el motor, el servicio privado y un transporte
para su integración posterior. No convierte v1 en un flujo validado todavía.

## Contrato

Servicio exclusivo v1: `validator.inventory_service:app`.
POST `/validate` autenticado con `Authorization: Bearer <token exclusivo v1>`.
JSON exacto: previous (PDF base64), candidate (PDF base64), baseSha256.
Se rechazan campos adicionales; nunca P12, PFX, contraseñas o claves privadas.
Respuesta positiva: política leapsign-v1.1-integrity-offline-1, hashes padre/hijo,
inventario completo, firma nueva, heredadas y estados independientes. Una imagen
o texto impreso no cuentan como firmas. La aceptación normal exige una nueva.
Confianza `not_evaluated`, revocación `unknown`: no existe política de confianza
configurada en v1. No se afirma vigencia al momento declarado, timestamp fiable
ni validez jurídica. La vigencia reportada se evalúa al recibir el PDF.

La política compara firmas CMS normalizadas para IDs, rangos originales,
integridad matemática, revisión cubierta y cambios semánticos permitidos.
El original exacto se conserva como prefijo y su hash se verifica de nuevo.
No se modifica ningún PDF. PDF cifrado, contenido activo, cobertura incompleta,
malformación o diferencia no verificable fallan cerrado.

## Límites y operación

- PDF individual: 10 MiB; 500 páginas; 128 revisiones; 64 firmas regulares.
- Lectura HTTP JSON: 29 MiB, 15 s; validación: 20 s; salida: 256 KiB.
- Una tarea simultánea por proceso, sin cola; hijo: CPU 15 s, AS 512 MiB.
- No usar réplicas para evadir cuotas globales; el transporte reserva en el
  ledger compartido antes de descargar el padre y de llamar al servicio.
- Cuotas iniciales: 200 validaciones/día globales, 50/propietario/día, 10/minuto
  globales; se consumen incluso con fallo. No son un tope de factura.
- Sin logs de acceso/cuerpos, persistencia de PDF, CORS ni documentación pública.
- TLS y aislamiento/egress deben configurarse en el proveedor; no hay un túnel
  de desarrollo ni un servicio público desplegado desde el entorno de Codex.

Configuración dedicada, nunca VITE ni secretos v2:

```text
PDF_SIGNATURE_INVENTORY_ENABLED=false
V1_PDF_VALIDATOR_TOKEN=<guardar directamente en secretos, nunca aquí>
V1_PDF_VALIDATOR_URL=https://<host-v1-aprobado>/validate
```

La bandera del servicio se habilitará solo para preparar readiness autenticada;
la bandera de aceptación del backend debe seguir apagada hasta la integración
atómica y las pruebas de humo. Actualmente ese enlace NO está implementado.
Un health 200 no equivale a una firma aceptada por el proceso.

Comando para el runtime aprobado (solo tras instalar las dependencias fijadas):

```sh
python -m uvicorn validator.inventory_service:app --host 127.0.0.1 --port 8092 --no-access-log
```

Usar un proxy TLS privado/autenticado del proveedor; no publicar directamente
ese puerto. El token se genera aleatoriamente y configura en ambos extremos sin
mostrarlo; no se ha generado un token antes de disponer del host.

## Verificación reproducible

```sh
python -m pip install -r validator/requirements-test.txt
python -m pytest validator/tests -q
npm test
npm run build
```

Las pruebas generan certificados y firmas únicamente en memoria. No hay raíces
de prueba instaladas en producción. La v1 existente sigue descargando para firmar
con la herramienta del usuario y subir solo el PDF: esta mejora NO añade un
formulario web P12 ni debe afirmar que ha firmado dentro del navegador.

Pendientes explícitos: revocación conocida/offline y política de confianza
operativa; pruebas FirmaEC/Adobe reales; concurrencia real de aceptación SQL;
recibos, RLS del inventario, UI del propietario y backfill controlado. Nunca
reescribir un documento histórico para forzar una relación demostrable.
